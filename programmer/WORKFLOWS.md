# 程序员工作流程模板

## 一、代码审查流程

### 触发条件
- Pull Request 创建
- 代码变更提交
- 定期代码质量检查

### 执行步骤

```yaml
workflow: code_review
steps:
  - name: 获取变更
    action: 分析 Git diff，识别变更文件
  
  - name: 分类审查
    parallel:
      - security_check:
          - SQL注入检测
          - XSS漏洞检测
          - 敏感数据处理检查
          - 权限验证检查
      - performance_check:
          - 循环效率分析
          - 数据库查询优化
          - 内存使用分析
      - maintainability_check:
          - 代码重复检测
          - 复杂度分析
          - 命名规范检查
  
  - name: 生成报告
    output:
      format: markdown
      sections:
        - 问题汇总（按严重程度）
        - 详细说明
        - 修复建议
        - 参考链接
```

### 输出模板

```markdown
# 代码审查报告

## 📊 概览
- 审查文件数: X
- 发现问题数: Y
- 严重程度: 高(A) / 中(B) / 低(C)

## 🔴 高优先级问题

### 1. [安全问题] SQL注入风险
- **文件**: `src/api/user.py:45`
- **问题**: 用户输入直接拼接到 SQL
- **建议**: 使用参数化查询
- **示例**:
  ```python
  # 修改前
  query = f"SELECT * FROM users WHERE id = {user_id}"
  
  # 修改后
  query = "SELECT * FROM users WHERE id = ?"
  cursor.execute(query, (user_id,))
  ```

## 🟡 中优先级问题
...

## 🟢 低优先级问题
...

## ✅ 做得好的地方
- 函数命名清晰
- 错误处理完善
...
```

## 二、重构流程

### 触发条件
- 代码审查发现重复代码
- 函数/类过大
- 复杂度过高

### 执行步骤

```yaml
workflow: refactor
steps:
  - name: 评估目标
    questions:
      - 重构目标是什么？
      - 当前测试覆盖率多少？
      - 风险等级评估
  
  - name: 制定计划
    output:
      - 重构步骤拆解
      - 每步验证方法
      - 回滚策略
  
  - name: 准备测试
    action: 确保有足够的测试覆盖
  
  - name: 小步执行
    loop:
      - 执行一个小改动
      - 运行测试确保通过
      - 提交代码
  
  - name: 验证完成
    checks:
      - 所有测试通过
      - 行为不变
      - 代码质量提升
```

### 重构检查表

```
□ 测试覆盖率 ≥ 80%
□ 每步改动可独立提交
□ 每步都有验证方法
□ 准备了回滚方案
□ 更新了相关文档
□ 通知了相关开发人员
```

## 三、调试流程

### 触发条件
- Bug 报告
- 错误日志
- 性能问题

### 执行步骤

```yaml
workflow: debug
steps:
  - name: 问题复现
    actions:
      - 收集问题详情
      - 确定复现步骤
      - 记录环境信息
  
  - name: 信息收集
    collect:
      - 错误日志
      - 错误栈
      - 相关代码
      - 数据库状态
  
  - name: 假设分析
    process:
      - 列出可能原因
      - 按可能性排序
      - 设计验证方法
  
  - name: 验证定位
    loop:
      - 选择一个假设
      - 执行验证
      - 记录结果
      - 排除或确认
  
  - name: 修复实施
    actions:
      - 编写修复代码
      - 编写测试用例
      - 代码审查
      - 部署验证
```

### 调试报告模板

```markdown
# Bug 调试报告

## 问题描述
- **症状**: 
- **影响范围**: 
- **严重程度**: 

## 根因分析
- **直接原因**: 
- **根本原因**: 
- **分析过程**: 

## 修复方案
- **修复代码**: 
- **测试用例**: 
- **验证结果**: 

## 预防措施
- **代码层面**: 
- **流程层面**: 
```

## 四、新功能开发流程

### 执行步骤

```yaml
workflow: feature_development
steps:
  - name: 需求分析
    outputs:
      - 功能描述
      - 验收标准
      - 技术方案
  
  - name: 设计评审
    checks:
      - API 设计
      - 数据库设计
      - 接口定义
  
  - name: 编码实现
    practices:
      - TDD 开发
      - 小步提交
      - 持续集成
  
  - name: 代码审查
    action: 提交 PR，进行代码审查
  
  - name: 测试验证
    tests:
      - 单元测试
      - 集成测试
      - E2E 测试
  
  - name: 发布部署
    steps:
      - 合并代码
      - 构建部署
      - 监控验证
```

## 五、技术债务处理流程

### 识别标准

```
代码味道                    优先级
─────────────────────────────────
重复代码                    高
过长函数 (>50行)            中
过大类 (>500行)             中
深层嵌套 (>3层)             高
魔法数字                    低
注释过多/过少               低
命名不清晰                  中
```

### 处理流程

```yaml
workflow: tech_debt
steps:
  - name: 债务识别
    tools:
      - 代码扫描工具
      - 复杂度分析
      - 代码审查发现
  
  - name: 优先级排序
    criteria:
      - 影响范围
      - 修改成本
      - 风险程度
  
  - name: 计划安排
    schedule:
      - 每周分配 20% 时间处理技术债务
      - 高优先级债务优先处理
      - 记录处理进度
  
  - name: 执行处理
    process:
      - 按重构流程执行
      - 更新技术债务清单
```

## 六、每日工作流

### 早间例行 (09:00-10:00)

```
□ 检查 CI/CD 状态
□ 查看待处理 PR
□ 回顾今日任务
□ 规划学习时间
```

### 编码时段 (10:00-12:00, 14:00-18:00)

```
□ 功能开发/问题修复
□ 代码自审
□ 编写/更新测试
□ 提交代码
```

### 晚间总结 (21:00-22:00)

```
□ 今日代码质量总结
□ 技术问题记录
□ 学习笔记整理
□ 明日计划制定
```

## 工作流配置说明

在 `career-config.json` 中可以自定义工作流：

```json
{
  "workflows": {
    "custom_flow": {
      "name": "自定义流程",
      "trigger": "手动触发",
      "steps": ["步骤1", "步骤2", "步骤3"],
      "output_format": "markdown"
    }
  }
}
```
